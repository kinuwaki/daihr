# daihr — 社内異動支援AI

人事担当者が異動案を作る際に、候補者・候補ポジションを根拠つきで提示するツールのPoC。
**AIは候補の発見と根拠の提示までを担当し、決定は人が行う**という前提で設計している。

あわせて、作りながら見つけた設計判断と落とし穴を
[解説動画](#解説動画) と [教科書](textbook/hr/ch01/index.html) にまとめてある。
再実装する人が同じ穴に落ちないための記録。

## 使い方

```bash
# UI（人事担当者向け）
python3 -m venv .venv
.venv/bin/pip install streamlit
.venv/bin/streamlit run src/app.py

# CLI（パイプライン全体の確認。依存ゼロで動く）
python3 src/run_poc.py

# 教科書・動画で述べている数値が実装と一致するかを検証
python3 src/test_claims.py
```

## この分野に定番OSSは無い

内部人材モビリティ／タレントマッチングには「これを使えば作れる」という
定番OSSが存在しない。市場は商用製品（Workday Talent Marketplace、Gloat、
Eightfold.ai、SAP SuccessFactors）が握っていて、コア部分はクローズド。

ただし構成要素ごとに標準はある。

| リソース | 用途 |
|---|---|
| 日本版O-NET（job tag） | 日本語で使える唯一の公的な職業データベース |
| ESCO | EUの多言語スキルオントロジー（約13,900スキル） |
| O*NET | 米労働省の職業DB。パブリックドメイン |
| Lightcast Open Skills | 約32,000スキルのタクソノミー |
| Fairlearn / AIF360 | 公平性検査 |

**精度はスキルをどう表現するかでほぼ決まる。**
自前で適当に作らず、公開されている体系を土台にする。

## 設計上の重要な判断

### 1. 保護属性を構造的に分離する

`schema.py` で `FEATURE_FIELDS` と `AUDIT_ONLY_FIELDS` を明示的に分けている。
性別・年齢はデータとしては持つが、マッチングの入力には流さず、
公平性検査でのみ参照する。**規約ではなく構造で守る。**

### 2. スコアは「加重和 × 必須スキル減衰」

単純な加重和にすると、**必須スキルがゼロでも本人希望と異動経路のスコアで
上位に来る**。推薦システムとしては通常の挙動だが、人事では使えない。
必須スキルを持たない人を候補に出した時点で担当者の信頼を失う。

```
必須充足率 = mean(min(1, 本人習熟度 / 必要習熟度))   # 必須スキルのみ
スキル適合 = 0.75 × 必須充足率 + 0.25 × 歓迎充足率

if 必須充足率 < SKILL_FLOOR:  除外            # ゲート（既定 0.30）

加重和 = 0.35×スキル + 0.20×評価 + 0.20×希望 + 0.15×経路 + 0.10×育成
総合   = 加重和 × (DAMPING_FLOOR + (1-DAMPING_FLOOR) × 必須充足率)
                                              # 減衰（既定 0.40）
```

減衰に下限を置くのは、ゲートを通った候補どうしの相対順位を保つため。
充足率をそのまま掛けると低充足の候補が潰れ、他のスコアの差が消える。

各スコアの定義:

| スコア | 定義 |
|---|---|
| スキル適合 | 上記のとおり。必須と歓迎は別フィールドで持つ |
| 評価適合 | コンピテンシー別評価と要求水準の適合。**未同意・未評価は中立0.5** |
| 本人希望 | 一致 1.0 / 方向違い 0.35 / **未記入 0.5**（未記入を不利にしない） |
| 異動経路 | 部署間の集約統計。最頻の異動先を1.0とする正規化。履歴なしは0.5 |
| 育成機会 | 平均ギャップ1.0を最良とする山形。完全充足は0.55 |

| 必須充足率 | 総合スコア |
|---|---|
| 0% | ゲート除外 |
| 25% | ゲート除外 |
| 50% | 0.300 |
| 100% | 0.562 |

閾値に理論的根拠は無い。だからこそ定数として外に出し、人事と調整できる形にしてある。

### 3. 公平性検査は比率だけで判定しない

Demographic Parity Ratio（4/5ルール）だけで判定すると、**小標本では
実体のない偏りを検出してしまう**。

実際に、年代と実力が完全に無相関なダミーデータでも parity ratio が
seed によって **0.20〜0.78** まで暴れることを確認した。これを「要調査」と
報告し続けると担当者は警告を無視するようになり、本物のバイアスを見逃す。
検査が厳しすぎるのではなく、検査が間違っている。

判定は次の2条件の **AND** にした。

1. parity ratio < 0.8（実務上の影響が大きい）
2. Bonferroni補正後の p値 < 0.05（偶然では説明しにくい）

検定は Fisher の正確確率検定（小標本に対応、外部依存不要）。scipy との一致を確認済み。

| | 補正前 | 補正後 |
|---|---|---|
| 誤報率（無相関データ） | 15% | **5%** |
| 検出力（実バイアス注入時） | — | **80%** |

補正後の 5% は有意水準 0.05 に見合う値。有意水準 5% で検定する以上、
無相関データでも 20 回に 1 回程度は有意と出る。ここを 0% に絞ると
検出力が落ちるので、名目水準に収まっていれば正しく機能している。

**公平性検査を入れただけで安心してはいけない。**
既知の答えを持つデータで、検査そのものを検証すること。

### 4. 除外理由を必ず残す

「なぜ推薦されなかったか」を説明できないシステムは人事では使えない。
本人開示請求や労組対応で必要になるため、ハードフィルタとゲートの
除外理由を全件記録し、UIから参照できるようにしている。

## 評価データの使い方

人事評価は**コンピテンシー別評価を職務適合の判定に使う**。
「課題発見力 4」「対人調整力 3」のような項目別の評価と、
ポジションが求めるコンピテンシー水準を突き合わせる。

スキル（何ができるか）とコンピテンシー（どう行動するか）は別軸なので、
スコアも分けている（重み 0.35 と 0.20）。

### 守っている三つの制約

1. **総合評価点は使わない** — 総合点でのランキングは異動支援ではなく選別。
   `Employee` に総合点のフィールドを持たせていない。項目別評価だけを持つ
2. **本人同意が無ければ参照しない** — `eval_consent` が False なら
   `usable_competencies()` が空を返し、評価を使わずに評価される
3. **評価が無い人を不利にしない** — 評価データが無い場合、
   コンピテンシースコアは中立の 0.5。ゼロにすると異動直後の社員や
   未同意の社員が構造的に候補から外れる

推薦理由には「評価で水準を満たすコンピテンシー」「水準未達の項目」を
明示するので、なぜその候補なのかを担当者が検証できる。

### 注意

評価データは処遇決定のために集めたものなので、異動推薦への利用は
**利用目的の確認が必要**。バイアスの固定化リスクもあるため、
公平性検査（後述）は評価を入れた状態で必ず回すこと。

詳細は [`docs/design.md`](docs/design.md)。

## サンプルデータの組織構造

`src/sample_data.py` の部署構成は **Daigasグループ（大阪ガス）の公開情報**を
土台にしている。**社員データそのものはすべて架空**（乱数生成）で、実データは含まない。

| セグメント | 部署 | 配属比率 |
|---|---|---|
| 国内エネルギー | ガス製造・エンジニアリング / 電力 / エナジーソリューション / ネットワーク | 46% |
| 海外エネルギー | 資源・海外 | 2% |
| ライフ&ビジネスソリューション | 都市開発 / 情報システム / ケミカル | 42% |
| コーポレート | 経営企画 / 事業創造 / DX企画 / 人事 / 財務 / 資材 | 10% |

配属比率は有報の従業員数（国内エネルギー 11,039 / 海外エネルギー 333 / LBS 10,463）
に合わせている。部署数で均等割りすると部署の多いコーポレートが最大勢力になり、
「少人数部署への異動」という現実的な状況が再現できない。

出典:
- [新機構表（2026年4月1日付）](https://www.osakagas.co.jp/company/press/pr2026/1798913_60968.html)
- 有価証券報告書 第208期（2026年3月期）
- Daigasグループ 人的資本レポート2025

**スキル定義は事業内容からの推定**で、社内の正式な分類ではない。
実運用では社内のタレントマネジメント分類に差し替えること。

## スキル名の表記ゆれ

実データではスキル名が必ず揺れる（「Python」「ｐｙｔｈｏｎ」「データ分析」「データ解析」）。
2段構えで吸収する。

1. **正規化** — NFKC・小文字化・記号除去。依存なしで動く
2. **意味的類似度** — `intfloat/multilingual-e5-large` をローカル実行。
   社内データを外部APIに送らない

**埋め込みは任意依存**にしてある。未導入なら文字類似度に落ちるだけで動く。
人事担当者に見せる段階で2GBのモデルを落とさせるのは筋が悪いため。

```bash
# 表記ゆれ吸収を有効にする場合のみ
.venv/bin/pip install sentence-transformers
```

### コサイン類似度をそのまま使ってはいけない

E5系のモデルは**無関係な語どうしでもコサインが0.8前後**出る。
素朴に `(cos + 1) / 2` で 0..1 に写すと「英語」と「簿記」が0.93になり、
**Pythonができる人が営業職に推薦される**。

無関係なスキル12語・全66ペアを実測して基準値を求めた。

| | コサイン |
|---|---|
| 無関係ペア | 最小0.728 / 中央0.798 / 最大0.878 |
| 同義ペア | 0.879〜0.963 |

**無関係の最大と同義の最小がほぼ接しており、単一の閾値では完全に分離できない。**
誤って同一視する方が実害が大きいので安全側に倒し、
弱い同義（法人営業↔B2B営業）は拾えないことを既知の限界として受け入れている。

この基準値は**モデル固有**なので、モデルを変えたら測り直すこと。

## 再実装する人へ

- **順序を間違えない** — 埋め込みや深層学習から入らない。
  ルールと単純な類似度で組んで、まず人事担当者に見せる。
  「この候補はおかしい」という反応が、どんな精度指標よりも価値がある
- **データ量が二桁足りない** — 論文のPJFモデルは大量の求人データが前提。
  数百人規模で深層学習しても過学習するだけ
- **スコアだけでは使えない** — 適合スキル・不足・本人希望との整合を
  言葉で出して、はじめて道具になる
- **公平性は最初から入れる** — あとから足すものではない。
  雇用分野のAIは EU AI Act でハイリスクに分類されている
- **AIは決定しない** — 候補の発見と根拠の提示まで。この境界を曖昧にすると
  技術的な問題が一気に人事上の問題に変わる
