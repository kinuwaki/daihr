# daihr — 社内異動支援AI

人事担当者が異動案を作る際に、候補者・候補ポジションを根拠つきで提示するツールのPoC。
**AIは候補の発見と根拠の提示までを担当し、決定は人が行う**という前提で設計している。

あわせて、作りながら見つけた設計判断と落とし穴を
[解説動画](#解説動画) と [教科書](textbook/hr/ch01/index.html) にまとめてある。
再実装する人が同じ穴に落ちないための記録。

## 使い方

```bash
# UI（人事担当者向け）
python3 -m venv .venv
.venv/bin/pip install streamlit
.venv/bin/streamlit run src/app.py

# CLI（パイプライン全体の確認。依存ゼロで動く）
python3 src/run_poc.py

# 教科書・動画で述べている数値が実装と一致するかを検証
python3 src/test_claims.py
```

## この分野に定番OSSは無い

内部人材モビリティ／タレントマッチングには「これを使えば作れる」という
定番OSSが存在しない。市場は商用製品（Workday Talent Marketplace、Gloat、
Eightfold.ai、SAP SuccessFactors）が握っていて、コア部分はクローズド。

ただし構成要素ごとに標準はある。

| リソース | 用途 |
|---|---|
| 日本版O-NET（job tag） | 日本語で使える唯一の公的な職業データベース |
| ESCO | EUの多言語スキルオントロジー（約13,900スキル） |
| O*NET | 米労働省の職業DB。パブリックドメイン |
| Lightcast Open Skills | 約32,000スキルのタクソノミー |
| Fairlearn / AIF360 | 公平性検査 |

**精度はスキルをどう表現するかでほぼ決まる。**
自前で適当に作らず、公開されている体系を土台にする。

## 設計上の重要な判断

### 1. 保護属性を構造的に分離する

`schema.py` で `FEATURE_FIELDS` と `AUDIT_ONLY_FIELDS` を明示的に分けている。
性別・年齢はデータとしては持つが、マッチングの入力には流さず、
公平性検査でのみ参照する。**規約ではなく構造で守る。**

### 2. スコアは「加重和 × 必須スキル減衰」

単純な加重和にすると、**必須スキルがゼロでも本人希望と異動経路のスコアで
上位に来る**。推薦システムとしては通常の挙動だが、人事では使えない。
必須スキルを持たない人を候補に出した時点で担当者の信頼を失う。

```
必須充足率 = mean(min(1, 本人習熟度 / 必要習熟度))   # 必須スキルのみ
スキル適合 = 0.75 × 必須充足率 + 0.25 × 歓迎充足率

if 必須充足率 < SKILL_FLOOR:  除外            # ゲート（既定 0.30）

加重和 = 0.45×スキル + 0.25×希望 + 0.20×経路 + 0.10×育成
総合   = 加重和 × (DAMPING_FLOOR + (1-DAMPING_FLOOR) × 必須充足率)
                                              # 減衰（既定 0.40）
```

減衰に下限を置くのは、ゲートを通った候補どうしの相対順位を保つため。
充足率をそのまま掛けると低充足の候補が潰れ、他のスコアの差が消える。

各スコアの定義:

| スコア | 定義 |
|---|---|
| スキル適合 | 上記のとおり。必須と歓迎は別フィールドで持つ |
| 本人希望 | 一致 1.0 / 方向違い 0.35 / **未記入 0.5**（未記入を不利にしない） |
| 異動経路 | 部署間の集約統計。最頻の異動先を1.0とする正規化。履歴なしは0.5 |
| 育成機会 | 平均ギャップ1.0を最良とする山形。完全充足は0.55 |

| 必須充足率 | 総合スコア |
|---|---|
| 0% | ゲート除外 |
| 25% | ゲート除外 |
| 50% | 0.286 |
| 100% | 0.580 |

閾値に理論的根拠は無い。だからこそ定数として外に出し、人事と調整できる形にしてある。

### 3. 公平性検査は比率だけで判定しない

Demographic Parity Ratio（4/5ルール）だけで判定すると、**小標本では
実体のない偏りを検出してしまう**。

実際に、年代と実力が完全に無相関なダミーデータでも parity ratio が
seed によって **0.20〜0.78** まで暴れることを確認した。これを「要調査」と
報告し続けると担当者は警告を無視するようになり、本物のバイアスを見逃す。
検査が厳しすぎるのではなく、検査が間違っている。

判定は次の2条件の **AND** にした。

1. parity ratio < 0.8（実務上の影響が大きい）
2. Bonferroni補正後の p値 < 0.05（偶然では説明しにくい）

検定は Fisher の正確確率検定（小標本に対応、外部依存不要）。scipy との一致を確認済み。

| | 補正前 | 補正後 |
|---|---|---|
| 誤報率（無相関データ） | 15% | **0%** |
| 検出力（実バイアス注入時） | — | **75%** |

**公平性検査を入れただけで安心してはいけない。**
既知の答えを持つデータで、検査そのものを検証すること。

### 4. 除外理由を必ず残す

「なぜ推薦されなかったか」を説明できないシステムは人事では使えない。
本人開示請求や労組対応で必要になるため、ハードフィルタとゲートの
除外理由を全件記録し、UIから参照できるようにしている。

## 評価データについて

**PoC段階では人事評価データを使っていない。** 理由は3つ。

1. **目的外利用のリスク** — 評価は処遇決定目的で収集されている
2. **バイアスの固定化** — 評価者バイアスをAIが学習して再生産する
3. **説明責任** — 本人開示請求時に説明が極めて困難になる

総合評価点でのランキングは異動支援ではなく選別なので避ける。
「まずスキルと本人希望だけで作りました」という状態は、法務・労組との
合意形成において強い立場になる。評価を足すのは合意が取れてから、
職務適合に直結する項目に限定するのが安全な順序。

詳細は [`docs/design.md`](docs/design.md)。

## 再実装する人へ

- **順序を間違えない** — 埋め込みや深層学習から入らない。
  ルールと単純な類似度で組んで、まず人事担当者に見せる。
  「この候補はおかしい」という反応が、どんな精度指標よりも価値がある
- **データ量が二桁足りない** — 論文のPJFモデルは大量の求人データが前提。
  数百人規模で深層学習しても過学習するだけ
- **スコアだけでは使えない** — 適合スキル・不足・本人希望との整合を
  言葉で出して、はじめて道具になる
- **公平性は最初から入れる** — あとから足すものではない。
  雇用分野のAIは EU AI Act でハイリスクに分類されている
- **AIは決定しない** — 候補の発見と根拠の提示まで。この境界を曖昧にすると
  技術的な問題が一気に人事上の問題に変わる
