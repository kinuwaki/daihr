# 他社の類似事例 — 技術ブログ・カンファレンス発表

「同じ課題に他社はどう取り組んでいるか」を、**論文ではなくエンジニアが書いた実装記録**から集めたもの。
学会論文のサーベイは [RecSys in HR 2025](recsys-in-hr-2025.md) / [2024](recsys-in-hr-2024.md)、
手法の整理は [スキル定義化・スキル正規化](skill-extraction-normalization.md) を参照。

出典はすべて実際に開いて内容を確認した。確認できなかったものは「未確認」と明記する。
本文書は調査結果の報告であり、採否の判断は含まない。

## 0. 先に結論

**探して分かった一番大きなこと：ビズリーチ（Visional）が2025年秋〜冬に、
日本語スキルマッチングのモデルを学習コードごと Apache 2.0 でOSS公開していた。**

日本語の公開資源は無い、というのが [survey.md](survey.md) 時点の結論だったが、
**この1点は更新される**。ただし公開されたのは*モデルと学習コード*であって、
スキル辞書（タクソノミー）ではない。

もう一つ。**「大企業が自社の異動マッチングを内製した」という開発者向け発表は、
探した範囲では見つからなかった。** この領域の技術的な公開情報は、
**HR事業者（作って売っている側）に集中している**。事業会社の情報発信は
人事向けカンファレンス（日本の人事部 HRカンファレンス等）に寄り、
そこでは技術の中身がほぼ語られない、という非対称がある。

| 分類 | 技術の中身が公開されているか |
|---|---|
| HR事業者（ビズリーチ、LinkedIn） | **公開されている**。モデル・評価・レイテンシまで |
| HR SaaSベンダー（Workday、Gloat、Eightfold等） | マーケティング資料のみ。「MLと知識グラフで」以上の記述なし |
| 事業会社の内製事例 | **ほぼ無い**。人事向け講演に留まり技術詳細が出ない |

## 1. ビズリーチ / Visional — 日本語で最も近い事例

社内異動ではなく**転職市場**の話だが、扱っている技術課題は社内異動とほぼ同じである。
そして**日本語**で、**実装レベル**まで書かれている唯一に近い情報源。

### 1.1 何が難しいかの整理

> [HR領域の検索が直面する課題 - 双方向マッチングの難しさと技術的挑戦](https://engineering.visional.inc/blog/660/bizreach-search-core-group/)
> 山本凌平（検索基盤グループ マネージャー）、2025年12月12日

この記事は**課題の言語化として質が高い**。挙げられている4点：

**(1) 双方向マッチングの構造的問題**

企業と求職者の双方が選び合うため、**片方の指標を最適化すると、もう片方が損なわれる**。
スカウト送信数を最大化すれば求職者に興味のない求人が増え、
応募数を最大化すれば企業要件に合わない応募が増える。

→ 社内異動では「本人の希望」と「受け入れ部署の要件」がこれに当たる。
   **単一の指標で評価してはいけない**ことの根拠として、そのまま使える。

**(2) 表記ゆれではなく「文脈」の問題**

同じ「RAG」というキーワードでも、

> 「月間100万クエリを処理する本番環境でRAG開発」と
> 「社内ドキュメント検索の試作でRAG検証」は全く異なる

→ **スキル名の正規化だけでは足りない**という指摘。
   スキルを持っているかではなく、どの深さで持っているか。
   スキル辞書を整備すれば解決する、という発想への反証になっている。

**(3) 異種データの統合**

構造化データ（年齢、勤務地）とテキスト（職務経歴書）と行動ログを統合する必要がある。
「Java, Spring」と「バックエンド開発経験」の対応付けが具体例として挙がっている。

**(4) Recall と Precision の両立**

採用担当者は「RAG」のみで検索すると15件、
「RAG OR ベクトルDB OR LLM」だと800件、というレンジで試行錯誤する。

### 1.2 採っている手法

- **SPLADE（疎ベクトル検索）** — 密ベクトルではなく疎ベクトルを選択
- **Interleaving** — 複数ランキングのオンライン比較評価
- 双方の指標を考慮したランキングロジック

### 1.3 OSS公開されたもの（重要）

> [日本語SPLADEモデルと学習コードのOSS公開](https://engineering.visional.inc/blog/721/bizreach-japanese-splade-oss/)
> Dat Nguyen（検索基盤グループ 機械学習エンジニア）、2025年11月11日

| 項目 | 内容 |
|---|---|
| モデル | `light-splade-japanese-14M` / `28M` / `56M` の3種 |
| 配布 | https://huggingface.co/collections/bizreach-inc/splade-68edb5856c83a1ba7e37bb1a |
| 学習コード | `light-splade`（PyTorch + HF Transformers、SPLADE v2 / SPLADE++、蒸留対応） |
| ライセンス | **Apache 2.0（商用利用可）** |

**なぜ密ベクトルではなくSPLADEなのか**（記事の理由）:

> 疎ベクトル表現を用いることで、従来の転置インデックスによる高速検索基盤を適用できる

加えて、**非ゼロ要素が特定の単語に対応するため説明可能性が確保できる**。

→ ここは社内異動の文脈で効く。[RecSys in HR](recsys-in-hr-2025.md) の実験が示すとおり
   「説明を出せば納得される」わけではないが、**なぜこの候補が出たかを
   人事担当者が単語レベルで追跡できる**のは、運用上の性質として別物である。
   密ベクトルだとこれができない。

※ 記事に定量評価の記載は**無い**。精度は自分で測る必要がある。

### 1.4 ドメイン特化のさせ方

> [HR領域の「言葉の壁」を越える。HRドメイン特化SPLADEモデル構築パイプラインの全貌](https://engineering.visional.inc/blog/728/hr-sparse-model-training-pipeline/)
> Dat Nguyen、2025年12月23日

**課題**：汎用モデルのトークナイザだと「Kubernetes」「法人営業」といったHR特有語が
細切れに分割され、**どの単語に重みを置いたかの解釈性が失われる**。

**3フェーズのパイプライン**：

| Phase | 内容 |
|---|---|
| 1. ドメイン適応事前学習 | 社内レジュメ・求人票で**語彙をゼロから再構築**。MeCab → WordPiece。cc100-ja / jawiki を経由し継続事前学習 |
| 2. 知識蒸留 | 検索ログのクエリ・文書ペアで Cross-Encoder を学習し、そのスコアをソフトラベル化 |
| 3. SPLADE微調整 | 蒸留損失 + FLOPS正則化。表現力と検索速度のトレードオフを制御 |

→ **Phase 2 が自社データを必要とする**点に注意。検索ログが無い段階では
   このパイプラインはそのまま再現できない。Phase 1 の語彙再構築は、
   独自の専門用語（設備名、事業領域名など）を持つ企業には効く可能性がある。

※ こちらも**定量評価の記載は無く**、「将来のA/Bテストで検証予定」とされている。

## 2. LinkedIn — スキルタクソノミーを実際に運用している唯一の公開事例

規模が違いすぎるので直接真似る対象ではないが、
**「スキル辞書を作って運用すると何が起きるか」の唯一のまとまった公開記録**である。

### 2.1 タクソノミーの構築と保守

> [Building and maintaining the skills taxonomy that powers LinkedIn's Skills Graph](https://www.linkedin.com/blog/engineering/data/building-maintaining-the-skills-taxonomy-that-powers-linkedins-skills-graph)
> Sofus Macskássy, Carol Jin, Shiyong Lin, Xiaomin Wei, Michael O'Neill、2023年3月21日

| 項目 | 数値 |
|---|---|
| スキル数 | **約39,000** |
| エイリアス（別名） | **374,000** |
| ロケール | 26 |
| スキル間の関係 | 200,000以上 |
| 成長 | 2021年2月から約35%拡大 |

**エイリアスがスキル本体の約10倍ある**、という比率が重要である。
スキル定義の作業量の大半は「何をスキルとするか」ではなく
**「同じスキルの言い換えを集めること」**に費やされている。

構造は**多重階層（polyhierarchy）**。1つのスキルが複数の親と子を持てる。
きれいな木構造にはならない、と実運用側が明言している。

作り方は3本柱：

1. **意味的フレームワーク** — 親子関係による「知識系統」
2. **人手のキュレーション** — 専門のタクソノミストが関係を付与。
   曖昧語（例：「Cadence」→「Cadence Software」）は利用メタデータを見て人が判断
3. **機械学習（KGBert）** — BERTベースで関係を予測。従来モデルより **F1で20%以上改善**

→ **最新のLLMを使っても人手のキュレーションは消えていない**、という点が
   実務上いちばん参考になる。39,000スキルの規模でも人が張り付いている。

活用側では、**子スキルを持つ人は親スキルもある程度持つと推論する**、という
階層の使い方が明記されている。

### 2.2 スキル抽出の本番運用

> [Extracting skills from content to fuel the LinkedIn Skills Graph](https://www.linkedin.com/blog/engineering/skills-graph/extracting-skills-from-content)
> Ji Yan（Tech Lead, LinkedIn AI）ほか、2023年12月13日

パイプラインは4段：

| 段階 | 内容 |
|---|---|
| 1. セグメンテーション | 文書を職務内容・応募資格・経験などに構造化し、**出現位置でスキルの重みを変える** |
| 2. タグ付け | **トークンベース**（タクソノミーをtrieで引く。速い）と**意味ベース**（Multilingual BERT の two-tower。「design of iOS application」→「Mobile Development」を推論）の**併用** |
| 3. 拡張 | Skills Graph で親・子・兄弟スキルに広げる |
| 4. スコアリング | 共有モジュール（文脈エンコーダ＋エンティティエンコーダ）＋ ドメイン別タワー |

**辞書引きと意味推論を併用している**点が実装上の要点である。
どちらか一方ではない。

**本番制約**：

- プロフィール編集が **毎秒約200件**
- 推論に **100ms未満**が要求される
- → **知識蒸留で12層BERTを80%削減**、性能を落とさずCPUサービングに載せた

**A/Bテストの効果**：

| 指標 | 改善 |
|---|---|
| 求人推薦（confirmed hires） | **+0.46%** |
| 求人検索（PPC収益） | +0.76% |
| スキルマッチング（qualified applications） | +0.87% |

→ **この数字の小ささは見ておく価値がある。** これだけの規模と投資で、
   採用成立への効果は **0.46%**。LinkedIn 規模では巨額だが、
   **年間数百件規模の社内異動に置き換えると、統計的に検出できない水準**である。
   [survey.md](survey.md) の「効果測定は自社で設計する前提」という論点を、
   数字の側から裏づけている。

## 3. サイバーエージェント — 配属最適化「ミカエル」

日本の事業会社で、**アルゴリズムによる人員配置を実運用した**数少ない公表事例。

> [サイバーエージェント、AIで新卒配属 170人と100部署を仲介](https://www.nikkei.com/article/DGXZQOUC1496B0U3A410C2000000/)（日本経済新聞、2023年4月）

- 2023年春から、ビジネス職**約170人**の配属決定に活用
- 新入社員の**第5志望まで**の希望と、各部署の募集をマッチング
- 従来は採用チームが約170人と100以上の事業部を仲介していた

**推薦ではなく「割当」である**点が、社内異動との重要な違いであり共通点でもある。
希望と定員がある両側マッチングで、一人を複数部署に配属できない。
社内異動でも、ポジションに定員がある以上、同じ構造が現れる。

**未確認**：
- 「一般化割当問題」という定式化は検索結果の要約に現れたが、**一次情報で確認できていない**
- 技術詳細（アルゴリズム、評価方法）を書いた**エンジニア発の記事は見つかっていない**
- 社内異動公募制度「キャリチャレ」および可視化システム「キャリバー」との関係も未確認

→ 報道ベースの情報に留まる。**技術的な参照先としては弱い。**

## 4. HR SaaSベンダー — 技術情報としては使えない

Workday、Gloat、Eightfold、365Talents、Fuel50、Phenom、Reejig といった
タレントマーケットプレイス製品群は、いずれも
「スキルオントロジー」「機械学習」「グラフ技術」を掲げている。

代表例：
- [The Foundation of the Workday Skills Cloud](https://blog.workday.com/en-us/foundation-workday-skills-cloud.html) — 「ユニバーサルなスキルオントロジー」「グラフ技術でスキル間の近さを保持」
- [AIで社内公募やプロジェクトと従業員をマッチング（リクルートワークス研究所）](https://www.works-i.com/research/labour/column/tm_tech/detail008.html) — Paddle、365Talents、Reejig 等の海外製品カタログ

**ただし、これらは全てマーケティング資料であり、
モデル・評価指標・失敗事例は一切公開されていない。**
競合分析には使えるが、技術的な参照先にはならない。

なお **リクルートワークス研究所のコラム**は、
海外タレントマネジメント製品の俯瞰としては比較的中立で、
「どんな製品カテゴリが存在するか」を把握する用途には使える。

## 6. まとめ — この調査で更新される認識

| これまでの認識 | 更新 |
|---|---|
| 日本語の公開資源は無い | **ビズリーチが日本語SPLADEモデル＋学習コードを Apache 2.0 で公開（2025年11月）**。ただしスキル辞書ではない |
| スキル辞書を作れば正規化できる | LinkedIn は**エイリアスがスキル本体の10倍**。作業の大半は言い換え収集。かつ**39,000規模でも人手キュレーションが残る** |
| 表記ゆれが主な課題 | ビズリーチは**「文脈・深さ」の問題**を挙げている。同じ「RAG」でも本番100万クエリと試作は別物 |
| 効果は出るはず | LinkedIn の A/B で**採用成立 +0.46%**。数百件規模では検出困難な水準 |
| 他社も内製しているはず | **事業会社の内製事例で技術詳細を公開したものは見つからなかった** |

### 実務上いちばん効く発見

**説明可能性のために疎ベクトル（SPLADE）を選ぶ**、というビズリーチの設計判断。

[RecSys in HR](recsys-in-hr-2025.md) の実験は「説明を出しても理解は向上しない」と示しているが、
それは**エンドユーザー向けの説明UI**の話である。
一方 SPLADE の解釈性は**開発・運用側がなぜこの結果になったかを追跡できる**という別の価値で、
こちらは実験に否定されていない。両者は矛盾しない。
