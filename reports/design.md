# 社内異動支援AI — 設計メモ

## 1. スコープ

**用途**: 人事側の異動案作成支援（トップダウン型）／まずPoC
**方式**: LLM + ベクトル検索によるハイブリッド推薦

人事担当者が「このポジションに合う人」「この人に合うポジション」を
候補リストとして受け取り、**最終判断は人間が行う**。
AIは意思決定者ではなく、候補の発見と根拠の提示に徹する。

## 2. アーキテクチャ

```
[ 職務記述書 ]──┐
[ 社員プロフィール ]─┼─▶ スキル正規化 ──▶ 埋め込み ──▶ ベクトルDB
[ 自己申告 ]────┘        (辞書 + LLM)      (embedding)    (faiss/pgvector)
                                                    │
[ 異動履歴 ]──▶ 協調シグナル ─────────────────────┤
                                                    ▼
                                          ハードフィルタ（等級/勤務地/必須資格）
                                                    ▼
                                          スコアリング & 再ランキング
                                                    ▼
                                          LLMによる根拠生成（推薦理由 / ギャップ）
                                                    ▼
                                          公平性チェック → 人事担当者へ提示
```

### 各層の責務

| 層 | 役割 | なぜここで分けるか |
|---|---|---|
| ハードフィルタ | 等級・勤務地・必須資格・異動不可フラグ | ルールで確実に落とす。LLMに任せると漏れる |
| ベクトル類似度 | スキル・経験の意味的な近さ | 表記ゆれ（「Python」「パイソン」「py」）を吸収 |
| 協調シグナル | 過去の類似異動パターン | 自社固有の「よくある異動経路」を反映 |
| 再ランキング | 各スコアの合成（加重和 × 必須スキル減衰） | 重みを外出しして人事と調整できるようにする |
| LLM説明生成 | 推薦理由とスキルギャップの言語化 | **スコアだけでは人事は使えない。理由が必要** |
| 公平性チェック | 属性別の推薦率の偏り検査 | 法務・労組対応の生命線 |

## 3. データ設計と取り扱い区分

| データ | 用途 | 取り扱い |
|---|---|---|
| 職務記述書 | 求人側の要件ベクトル | 制約なし |
| スキル定義 | 正規化辞書 | 制約なし |
| 自己申告・キャリア希望 | 本人の意向。**最優先シグナル** | 本人が提供したもの＝目的が明確 |
| 異動履歴 | 協調フィルタリングの教師 | 部署単位に集約すれば個人特定を回避できる |
| **人事評価データ** | **要検討（下記）** | **最大の論点** |

### 人事評価データの扱い — 最重要論点

「評価が見れる」からといって、そのまま推薦モデルに投入するのは危険です。

**リスク**
1. **目的外利用**: 評価は「処遇決定」目的で収集されている。異動推薦への転用は
   利用目的の範囲外になる可能性がある（個人情報保護法 第18条）
2. **バイアスの増幅**: 過去の評価に評価者バイアスが含まれる場合、
   AIがそれを学習して固定化する。「高評価者だけが異動機会を得る」構造ができる
3. **説明責任**: 「なぜ推薦されなかったか」に評価が絡むと、
   本人開示請求時に極めて説明が難しくなる

**推奨する設計**
- **第1段階（PoC）**: 評価データを**使わない**。スキル・経験・本人希望のみで組む。
  これで十分な精度が出るケースは多い
- **第2段階**: 使う場合も「生の評価点」ではなく
  「特定領域のコンピテンシー評価」など**職務適合に直接関係する項目に限定**
- **絶対に避ける**: 総合評価点でのランキング。それは異動支援ではなく選別

PoC段階で評価データを外しておくと、**法務・労組との合意形成が圧倒的に楽**になります。
「まず本人希望とスキルだけで作りました」は強い立場です。

### スコア合成の設計（重要）

当初は単純な加重和にしていたが、PoCで実際に回したところ
**必須スキルがゼロなのに、本人希望と過去の異動経路だけで上位に来る候補**が発生した。
人事担当者に一度でもこれを見せると信頼を失うため、2つの対策を入れてある。

1. **ゲート** (`SKILL_FLOOR = 0.30`) — 必須スキル充足率が3割未満の候補は推薦しない。
   除外理由は監査ログに残す
2. **減衰** — 総合スコア = 加重和 × (0.4 + 0.6 × 必須スキル充足率)。
   ゲートを通過しても、充足率が低い候補が満点候補と並ばないようにする

いずれも定数を外出ししてあるので、人事との対話で調整できる。

## 4. 公平性の担保

- 性別・年齢・国籍などの**保護属性はモデル入力から除外**（間接的な代理変数にも注意）
- 属性別の**推薦率の偏り**を定期測定（demographic parity / equal opportunity）
- 「推薦されなかった人」のログも保持し、監査可能にする
- EU AI Act では雇用分野のAIは **ハイリスク** 分類。国内でも経産省
  「AI事業者ガイドライン」に沿った説明責任の設計が必要

## 6. PoCの評価方法

過去の異動履歴を**ホールドアウト**して精度を測る:
- 直近1年の異動を隠し、それ以前のデータでモデルを作る
- 「実際に異動した先」が推薦上位N件に入る割合 = Recall@N
- ただし**過去の異動が正解とは限らない**点に注意。
  過去が偏っていればモデルもそれを再現する。定量指標と併せて人事担当者の
  目視評価（「この候補は納得感があるか」）を必ず取る
